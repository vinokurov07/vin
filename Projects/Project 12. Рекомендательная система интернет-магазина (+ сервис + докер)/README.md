## Постановка задачи

**Бизнес-цель:** повысить прибыль от допродаж на 20% через персонализированные 
рекомендации на главной странице интернет-магазина.

**Техническая метрика:** Precision@3 — доля пользователей, у которых купленный 
товар попал в топ-3 рекомендаций.

**Формат рекомендаций:** 3 товара на главной странице.

## Исходные данные

**Источник данных:** [Retailrocket recommender system dataset](https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset) .
Инструкция по загрузке — в [scripts/download_data.md](scripts/download_data.md).

Датасет состоит из трёх таблиц:

| Таблица | Формат | Описание | Объём |

| `events.csv` | CSV | События пользователей: просмотр, корзина, покупка | 2.75 млн строк |

**Колонки item_properties:**
- `timestamp` — момент записи свойства
- `itemid` — ID товара
- `property` — название свойства (`categoryid` или хеш)
- `value` — значение

**Колонки category_tree:**
- `categoryid` — ID категории
- `parentid` — ID родительской категории (NaN для корневых)

- 87% пользователей имеют <10 событий — массовый холодный старт

## Трансформации и подготовка выборок

### Целевая переменная

Для каждой пары `(пользователь, товар)` в момент времени `T` строим бинарную метку:

- `target = 1`, если пользователь купил этот товар в течение 24 часов после `T`;
- `target = 0` иначе.

**Почему 24 часа.** Из EDA: медиана времени от первого события до покупки — 0.31 часа (~19 минут), 75-й перцентиль — 4.6 часа. Значит, большинство покупок происходит быстро, в рамках текущей сессии. Окно 24 часа покрывает почти все реальные покупки, при этом не «размазывая» метку на слишком долгий срок.

**Как строим.** Функция `add_target_precise` проверяет **все** транзакции пользователя в окне 24 часа, а не только ближайшую (в отличие от `merge_asof`). Это корректно обрабатывает:
- покупки нескольких товаров в одной транзакции;
- случаи, когда между просмотром и покупкой была промежуточная транзакция другого товара.

### Разделение по времени

| Набор | Период | Строк | Уникальных пользователей |
|-------|--------|-------|--------------------------|
| **Train** | до 17.08.2015 | ~164 000 | ~27 300 |
| **Validation** | 18–31.08.2015 | ~17 000 | ~2 800 |
| **Test** | 01–17.09.2015 | ~126 300 | ~1 260 |

**Почему размеры такие.** Число строк сбалансировано, но **структура разная**:

- **Train/Val**: 6 строк на пользователя (1 позитив + 5 сэмплированных hard-негативов). Всего строк много за счёт большого числа пользователей.
- **Test**: 100 строк на пользователя (1 позитив + 99 негативов). Пользователей меньше (только те, у кого была покупка в тестовом окне), но каждый даёт в 16 раз больше строк.

Итог: 164k vs 126k — это **не «сопоставимые выборки»**, а разные по смыслу. Train — про **обучение на пользователях**, test — про **оценку метрики Precision@3** (100 кандидатов на пользователя).

### Типы негативов

**Train/Val — hard negatives.** Все негативы — это **просмотренные, но не купленные** товары. Мы не сэмплируем случайные товары из каталога, потому что это делает задачу тривиальной: у случайных товаров все `user_item_*` признаки равны нулю, и модель просто выучивает правило «если пользователь смотрел товар → покупай».

**Почему hard:** задача рекомендательной системы — отличать **интересный** товар (тот, который купят) от товара, который пользователь видел и **не заинтересовался**. Именно так работает главная страница: пул кандидатов пересекается с историей пользователя. Пробовал на easy negatives, в этом случае модель просто выучивает правило «просмотрено → покупай», и Precision@3 достигает 1.0. Это не отражает реальное качество.

**Балансировка 1:5.** Все позитивы сохраняем, из негативов сэмплируем 5 на каждый позитив. Это уменьшает доминирование класса 0 (изначально 1:77) и ускоряет обучение.

**Test — hard с fallback на easy.** Строим так:

1. Для каждого пользователя с покупкой — 1 позитив (купленный товар).
2. 99 негативов — сначала hard (просмотренные, но не купленные до момента покупки).
3. Если hard-негативов меньше 99 (а это происходит у 87% пользователей с историей <10 просмотров), добиваем **случайными товарами из каталога (easy)**.

Это отражает реальность: у типичного пользователя короткая история, и система вынуждена рекомендовать из всего каталога.

### Признаки

**Item-факторы** (по товару):
- **Статические:** `categoryid`, `parent_category_id`, `num_properties`, бинарные признаки топ-20 свойств, `is_top_category`, `category_depth`.
- **Динамические дневные:** скользящие суммы просмотров / корзин / покупок за 1/7/30 дней; CTR, CVR, тренды, свежесть.
- **Динамические часовые:** скользящие суммы за 1/6/12 часов.

**User-факторы** (по пользователю):
- Дневные агрегаты активности за 1/7/30 дней.
- Признаки сессии: номер события, время с начала сессии.
- Временные: час, день недели, время суток.

**User-item-факторы** (по паре):
- История взаимодействий пользователя с конкретным товаром за 1/7/30 дней.

**Временной сдвиг.** Все динамические признаки сдвинуты на 1 день (или 1 час для часовых), чтобы не было утечки из будущего. Для даты `D` признак `view_last_7d` содержит просмотры за 7 дней **до** `D`, не включая сам день `D`.

### Удалённые признаки (утечки)

В процессе экспериментов удалил три типа признаков — каждый из них искажал метрику:

| Признак | Почему удалили |
|---------|----------------|
| `visitorid`, `itemid` | Высококардинальные ID: модель запоминала конкретных пользователей и товары вместо обобщения. Работает в train, но не на новых пользователях (холодный старт) |
| `days_since_*` | Вычислялись **после** временного сдвига, но не сдвигались сами. Из-за этого у 100% позитивов принимали значение 0, а у негативов — тоже 0, но по другой причине. Модель получала ложный сигнал |
| `*_transaction_*` | Разное распределение в train и test: в train негативы — просмотры без покупки (у них `transaction_*` часто > 0), в test 85% негативов — easy (у них `transaction_*` = 0). Модель училась на смещении, которое в тесте не работает |

## Построение валидации

### Разделение по времени

```
Train:        до 2015-08-17
Validation:   2015-08-18 — 2015-08-31
Test:         2015-09-01 — 2015-09-17
```

**Почему по времени, а не случайно.** Рекомендательные системы чувствительны к изменению предпочтений. Случайное разделение (`train_test_split(shuffle=True)`) приводит к **утечке из будущего**: модель видит события из тестового периода во время обучения и показывает завышенные метрики. Хронологическое разделение эмулирует реальную ситуацию: обучаемся на прошлом, тестируемся на будущем.

### Метрика Precision@3

**Задача:** для каждого пользователя с покупкой в тестовый период нужно угадать, какой товар он купит, показав 3 варианта.

**Протокол оценки:**

1. Для каждого пользователя с покупкой формируем **100 кандидатов**: 1 реально купленный товар (позитив) + 99 негативов.
2. Модель предсказывает вероятность покупки для каждого кандидата.
3. Сортируем по убыванию вероятности, берём **топ-3**.
4. Если купленный товар попал в топ-3 — успех для этого пользователя.

**Precision@3** = доля пользователей, у которых это произошло.

- Случайный уровень для 100 кандидатов: 3/100 = **0.03**.
- Оценка только по пользователям с покупкой (остальные не вносят вклад в метрику).
- Если у пользователя несколько покупок — берём одну случайную, чтобы не дублировать пользователя в оценке.

### Состав тестовой выборки: важный нюанс

Построил тест так: 1 позитив + 99 негативов, причём негативы — **сначала hard, потом easy (fallback)**. Это создаёт проблему интерпретации:

Проверка пользователей теста показала:

- **87% имеют <10 просмотров** до покупки (медиана — 2).
- Для этих 87% **99 hard-негативов набрать невозможно** — у них просто нет столько просмотренных товаров. Значит, они добиваются easy.

Итог: тест `test_pairs_df` — **смесь** примерно 85% easy-негативов и 15% hard.

**Что это означает для метрики.** На easy-негативах тривиальное правило работает почти идеально:

- У easy-негативов `item_daily_addtocart_last_7d` = 0 (товар вообще не фигурировал в каталоге).
- У позитивов этот признак часто > 0 (товар был популярен и просмотрен).

Правило «самый популярный из 100» на таком тесте даёт Precision@3 ≈ **0.87**. Это **завышенная** оценка — тривиальное правило не должно побеждать обученную модель.

### Strict hard — честная оценка

Чтобы получить честную метрику, вводим подвыборку **strict hard** — только пользователи с ≥10 просмотрами (152 из 1194). У них достаточно истории, чтобы набрать 99 hard-негативов.

На этой выборке:

- Все негативы — реальные hard (просмотренные, но не купленные).
- Правило «самый популярный» даёт ≈ **0.51** (вместо 0.87).
- Метрика отражает **реальную задачу**: различить купленный товар от просмотренного, но не заинтересовавшего.

**В отчёте приводим обе метрики** — полную (смешанную, `test_pairs_df`) и strict hard (152 пользователя). Это показывает, как состав теста влияет на результат, и даёт честную картину качества.

### Сводка по метрикам

| Метод | Full test (смесь) | Strict hard |
|-------|-------------------|-------------|
| Бейзлайн popular | 0.87 | 0.51 |
| CatBoost | — | 0.42 |
| **Гибрид** | — | **0.63** |

Случайный уровень для обоих тестов = **0.03**.

## Эксперименты и результаты

Эксперименты проводились итеративно. На каждом шаге смотрел Precision@3 на strict hard и feature importance, удаляя признаки, которые давали утечку или мешали модели.

### 1. Бейзлайны

**Случайный выбор.** Для каждого пользователя случайно выбираем 3 товара из 100 кандидатов. Ожидаемый Precision@3 = 3/100 = **0.03**. Проверка корректности протокола оценки.

**Популярность.** Сортируем кандидатов по `item_daily_addtocart_last_7d` (популярность товара по добавлениям в корзину за неделю), берём топ-3. Необучаемое правило — модель не тренируется, просто «самый популярный из 100».

Результаты:
- На **полном тесте** (смесь easy и hard) — **0.87**. Тривиальное правило ломает задачу, потому что easy-негативы имеют популярность = 0.
- На **strict hard** — **0.51**. Это реалистичная нижняя граница, которую должна побить модель.

### 2. CatBoost: итеративное улучшение

Обучаем CatBoost несколько раз, последовательно удаляя признаки-утечки.

| Шаг | Признаки | Precision@3 (strict hard) |
|-----|----------|---------------------------|
| 1 | Все признаки + `visitorid`, `itemid` | Высокий (утечка через запоминание) |
| 2 | Без ID | 0.21 |
| 3 | Без ID, без `days_since_*` | 0.33 |
| 4 | Без ID, без `days_since_*`, без `transaction_*` | 0.42 |

**Что происходило на каждом шаге:**

- **Шаг 1 → 2.** `visitorid` и `itemid` позволяли модели запоминать конкретных пользователей и товары. Это даёт прирост на train и на известных пользователях, но не обобщается. Персональные сигналы сохранены через `user_item_daily_*`, которые работают и для новых пользователей.
- **Шаг 2 → 3.** `days_since_*` вычислялись после временного сдвига и не сдвигались сами. У 100% позитивов значение = 0 (транзакция «произошла сегодня»), у большинства негативов — тоже 0. Модель вцепилась в признак (38% важности), но сигнал был ложным.
- **Шаг 3 → 4.** `*_transaction_*` имели разное распределение в train и test. Модель училась на смещении, которое в тесте не работало.

### 3. Почему CatBoost проиграл бейзлайну

На strict hard: CatBoost = 0.42, бейзлайн популярности = 0.51. **Обученная модель хуже тривиального правила.**

Это не ошибка — это следствие **рассогласования train и test**:

- **В train** негативы — hard (просмотры без покупки). У них `addtocart_last_7d` тоже часто > 0 (товар был популярен). Признак **слабо разделяет классы**, и модель учится на него не опираться.
- **В test** 85% негативов — easy, у которых `addtocart_last_7d` = 0. Здесь этот признак — идеальный разделитель. Бейзлайн использует его напрямую.
- CatBoost, обученный на train, не может «переключиться» на этот сигнал в тесте.

### 4. Гибрид (retrieval + ranking)

**Идея.** Не заставлять CatBoost учиться на популярности (она плохо работает в train). Вместо этого — разделить задачу:

1. **Retrieval.** Из 100 кандидатов (1 реально купленный товар + 99 смотрел, но не купил) отбираем топ-20 по популярности (`item_daily_addtocart_last_7d`) — необучаемое правило. Быстро отсеивает мусор.
2. **Ranking.** На этих 20 кандидатах запускаем CatBoost, получаем вероятности покупки.
3. **Топ-3.** Сортируем по вероятности, берём финальные 3 товара.

**Подбор гиперпараметров.** Перебрал 6 скоров для retrieval × 5 значений `preselect` = 30 комбинаций. Лучший результат:

- `score = item_daily_addtocart_last_7d`
- `preselect = 20`
- Precision@3 = **0.63**

**Почему это работает.** Популярность и персонализация **дополняют** друг друга:

| Модель | Precision@3 |
|--------|-------------|
| CatBoost один | 0.42 |
| Бейзлайн популярности | 0.51 |
| **Гибрид** | **0.63** |

Гибрид лучше каждого компонента в отдельности. Это подтверждает стандартную архитектуру рекомендательных систем: сначала быстрый retrieval, потом сложный ranking.

### 5. Оптимизация гиперпараметров (Optuna)

Подбирал гиперпараметры CatBoost с помощью Optuna (`n_trials=20`), оптимизируя AUC на валидации. Лучшие параметры:

- `iterations = 3000`, `learning_rate = 0.0106`, `depth = 10`
- `l2_leaf_reg = 2.51`, `random_strength = 0.001`
- `bagging_temperature = 0.759`, `min_data_in_leaf = 74`

**Проверка переобучения:**

- Logloss train (best iter 1433): 0.267
- Logloss val (best iter 1433): 0.339
- **Разница: 0.072** — модель хорошо обобщает.

Модель не переобучена (разница < 0.1), не недообучена (best iter на середине диапазона), AUC = 0.83 на валидации.

### 6. Итоговое сравнение

**Основная таблица (strict hard — честная оценка):**

| Метод | Precision@3 |
|-------|-------------|
| Случайный выбор | 0.030 |
| CatBoost (с утечками через IDs) | — (иллюзия) |
| CatBoost (без IDs) | 0.214 |
| CatBoost (без IDs, без `days_since_*`) | 0.334 |
| CatBoost (clean, без IDs/`days_since`/`transaction`) | 0.415 |
| CatBoost (Optuna) | 0.507 |
| Бейзлайн популярности | 0.507 |
| **Гибрид (popularity → CatBoost)** | **0.645** |

**Победитель — гибрид:** +14 п.п. к бейзлайну и +14 п.п. к чистому CatBoost. Это **в 21 раз лучше случайного уровня**.

**Разные тесты — разные метрики:**

| Метод | Full test (смесь) | Strict hard |
|-------|-------------------|-------------|
| Бейзлайн popular | 0.869 | 0.507 |
| CatBoost (Optuna) | — | 0.507 |
| Гибрид | 0.791 | 0.645 |

На полном тесте бейзлайн популярности выигрывает, потому что 85% негативов — easy. На strict hard побеждает гибрид. Это показывает, что **выбор тестовой выборки критически влияет на результат**, и для честной оценки нужен strict hard.

## Архитектура сервиса

Сервис — это Flask-приложение с гибридной моделью (retrieval + CatBoost). Он принимает HTTP-запросы, прогоняет кандидатов через модель и возвращает топ-3 рекомендации.

### Компоненты

| Компонент | Роль |
|-----------|------|
| **Flask** | HTTP API, валидация запросов, метрики Prometheus |
| **RecommenderModel** | Загрузка модели и snapshot популярности, гибридная логика |
| **CatBoost** | Ранжирование кандидатов по вероятности покупки |
| **Retrieval** | Быстрый отбор топ-20 по популярности до CatBoost |
| **Gunicorn** | Production WSGI-сервер (вместо dev-сервера Flask) |

### Структура проекта

```

├── app/
│   ├── __init__.py
│   ├── main.py              # Flask-приложение, эндпоинты

### Схема работы

```
Клиент
  │
  │ POST /recommend {visitorid, candidates}
  ▼
┌─────────────────────────────────────────┐
│ Flask (main.py)                         │
│  1. Валидация запроса                   │
│  2. DataFrame из candidates             │
│  3. model.recommend(df)                 │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│ RecommenderModel                        │
│  1. merge со snapshot популярности      │
│  2. Retrieval: top-20 по popularity     │
│  3. CatBoost: predict_proba на top-20   │
│  4. Top-3 по вероятности                │
└────────────────┬────────────────────────┘
                 │
                 ▼
Клиент получает {"recommendations": [...], "model_version": "1.0.0"}
```
То есть **признаки насчитываются на стороне клиента**. В качестве MVP примем такой вариант.

### Логика инициализации

Модель и snapshot популярности загружаются **один раз** при старте сервиса (в `RecommenderModel.__init__`). Каждый последующий запрос обрабатывается мгновенно, потому что модель уже в памяти.

Инициализация вынесена в момент старта, чтоб не загружать модель при каждом запросе,тогда сервис работал бы медленнее.

### Логика запроса

1. **Валидация.** Проверяем, что тело — JSON, `candidates` — непустой список ≤1000, каждый кандидат — объект с `itemid`. Некорректные запросы возвращают 400 с описанием ошибки.
2. **Подготовка данных.** `pd.DataFrame(candidates)` — из JSON делаем таблицу. Недостающие признаки заполняются нулями (модель должна работать и на неполных данных).
3. **Retrieval.** Сортируем кандидатов по `item_daily_addtocart_last_7d` (популярность товара за неделю), оставляем топ-20.
4. **Ranking.** Прогоняем топ-20 через CatBoost, получаем вероятности покупки, сортируем по убыванию.
5. **Ответ.** Возвращаем топ-3 `itemid` в формате JSON.

## Запуск через Docker

### Требования

- Docker 20.10+
- Свободное место на диске: ~2 ГБ
- Свободный порт 8000

### Быстрый старт

**1. Загрузите образ из `.tar`:**

```bash
docker load -i recommender.tar
```

Ожидаемый вывод:
```
Loaded image: recommender:1.0.0
```

**2. Запустите контейнер:**

```bash
docker run -d -p 8000:8000 --name recommender recommender:1.0.0
```

Флаги:
- `-d` — в фоне (detached)
- `-p 8000:8000` — проброс порта: 8000 на хосте → 8000 в контейнере
- `--name recommender` — имя контейнера (для удобства)
- `recommender:1.0.0` — образ

**3. Проверьте, что сервис работает:**

```bash
curl http://localhost:8000/health
# {"status": "ok"}
```

**4. Отправьте тестовый запрос:**

```bash
curl -X POST http://localhost:8000/recommend \
  -H "Content-Type: application/json" \
  --data-binary "@tests/valid.json"
```

Ожидаемый ответ:

```json
{"recommendations": [101, 303, 202], "model_version": "1.0.0"}
```

### Что внутри образа

- Python 3.10 (базовый образ `python:3.10-slim`)
- Flask, CatBoost, pandas, numpy, pyarrow, prometheus-client, gunicorn
- Модель `catboost_best.cbm`
- Snapshot популярности `item_popularity.parquet`
- Код приложения в `/app/app/`

## API сервиса

Базовый URL: `http://localhost:8000`

### POST /recommend

Возвращает топ-3 рекомендации для пользователя.

**Тело запроса:**

```json
{
  "visitorid": 12345,
  "candidates": [
    {
      "itemid": 101,
      "categoryid": 5,
      "parent_category_id": 2,
      "hour": 20,
      "dayofweek": 4,
      "is_weekend": 0,
      "day_period": "Evening",
      "session_event_num": 1,
      "time_since_session_start": 0.0
    },
    {
      "itemid": 202,
      "categoryid": 7,
      "hour": 20,
      "dayofweek": 4,
      "day_period": "Evening"
    }
  ]
}
```

**Обязательные поля:**

- `candidates` — непустой список объектов, не более 1000 штук
- у каждого объекта — поле `itemid`

**Опциональные поля:**

Все остальные признаки из обучающего набора (item-, user-, user-item-признаки). Недостающие заполняются нулями. **Чем больше признаков передадите, тем точнее ранжирование.**

**Успешный ответ (HTTP 200):**

```json
{
  "recommendations": [101, 303, 202],
  "model_version": "1.0.0"
}
```

`recommendations` — список `itemid` в порядке убывания вероятности покупки. Длина списка = `min(3, len(candidates))`.

### Пример запроса через `curl`

```bash
curl -X POST http://localhost:8000/recommend \
  -H "Content-Type: application/json" \
  --data-binary "@tests/valid.json"
```

```

### Обработка ошибок

Сервис устойчив к некорректным запросам. Все ошибки возвращают код **400** и JSON с описанием:

| Запрос | Ответ | Код |
|--------|-------|-----|
| `{}` | `{"error": "'candidates' must be a list"}` | 400 |
| `{"candidates": "not a list"}` | `{"error": "'candidates' must be a list"}` | 400 |
| `{"candidates": []}` | `{"error": "'candidates' must not be empty"}` | 400 |
| `{"candidates": [101, 202]}` | `{"error": "Each candidate must be an object"}` | 400 |
| `{"candidates": [{"categoryid": 5}]}` | `{"error": "Each candidate must have 'itemid'"}` | 400 |
| `{ невалидный JSON` | `{"error": "Request body must be valid JSON"}` | 400 |
| >1000 кандидатов | `{"error": "'candidates' must not exceed 1000 items"}` | 400 |

**Примеры для проверки** лежат в папке `tests/`:

| Файл | Что проверяет |
|------|---------------|
| `tests/valid.json` | Успешный запрос |
| `tests/empty.json` | Пустое тело |
| `tests/not_list.json` | `candidates` не список |
| `tests/empty_list.json` | Пустой список кандидатов |
| `tests/not_object.json` | Кандидат — не объект |
| `tests/no_itemid.json` | Кандидат без `itemid` |
| `tests/invalid.json` | Невалидный JSON |

**Запуск всех проверок:**

```bash
curl -X POST http://localhost:8000/recommend -H "Content-Type: application/json" --data-binary "@tests/empty.json"
curl -X POST http://localhost:8000/recommend -H "Content-Type: application/json" --data-binary "@tests/not_list.json"

## Метрики и мониторинг

Сервис предоставляет метрики в формате Prometheus через эндпоинт `/metrics`. Их можно собирать в Prometheus и визуализировать в Grafana.

### Доступные метрики

| Метрика | Тип | Описание |
|---------|-----|----------|
| `requests_total{endpoint, status}` | Counter | Всего запросов на эндпоинт |
| `request_duration_seconds{endpoint}` | Histogram | Время обработки запроса |
| `predictions_total` | Counter | Всего предсказаний модели |
| `python_gc_objects_collected_total` | Counter | Стандартные метрики Python |

### Пример вывода

```
# HELP requests_total Total requests
# TYPE requests_total counter
requests_total{endpoint="/recommend",status="200"} 42.0

# HELP request_duration_seconds Request duration
# TYPE request_duration_seconds histogram
request_duration_seconds_bucket{endpoint="/recommend",le="0.05"} 40.0
request_duration_seconds_bucket{endpoint="/recommend",le="0.1"} 42.0
...

# HELP predictions_total Total predictions
# TYPE predictions_total counter
predictions_total 42.0
```

### Проверка метрик

```bash
curl http://localhost:8000/metrics | grep predictions_total
```

После нескольких запросов `/recommend` счётчик `predictions_total` увеличивается.

### Подключение Prometheus

Создать `prometheus.yml`:

```yaml
scrape_configs:
  - job_name: 'recommender'
    scrape_interval: 15s
    static_configs:
      - targets: ['localhost:8000']
```

Если запустить Prometheus с этим конфигом — он начнёт собирать метрики с сервиса каждые 15 секунд.

## Ограничения и направления развития

1. **Feature store.** В текущей версии признаки для кандидатов формирует клиент. В проде логичнее вынести это в отдельный компонент (feature store), а сервис получал бы только `visitorid` и список `itemid`. Но в качестве MVP примем, что признаки насчитыаются на стороне клиента.
2. **Обновление snapshot популярности.** Сейчас snapshot фиксирован на 2015-08-17. В проде его нужно пересчитывать регулярно (раз в день/час).
3. **A/B-тест.** Precision@3 — офлайн-метрика. Реальное влияние на прибыль проверяется только A/B-тестом.
4. **Больше first-stage скоров.** Retrieval сейчас использует только `addtocart_last_7d`. Можно попробовать композицию из нескольких скоров.
